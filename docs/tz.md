**Проект:** Turon B2C
**Документ:** ТЗ v1 · схема данных · метрики
**Дата:** 28.08.2026

---

## 1. Задача

Руководитель отдела продаж (РОП) и менеджеры работают по одним и тем же
заявкам, но нуждаются в разных срезах:

* **РОП** — картина по отделу: кто сколько продал, где проседает воронка,
  выполняется ли план, что горит прямо сейчас.
* **Менеджер** — свой личный результат: мой план и факт, мои заявки, что
  надо сделать сегодня.

Сейчас учёт ведётся в Google-таблице. Дашборд не заменяет её на первом
этапе, а читает и превращает в управленческую картинку.

**Что делаем:** веб-приложение с авторизацией, двумя ролями и общим набором
экранов, у которых меняется область видимости данных.

## 2. Роли и доступ

| | РОП | Менеджер |
|---|---|---|
| Свои сделки и клиенты | ✅ | ✅ |
| Сделки других менеджеров | ✅ | ❌ |
| Рейтинг команды поимённо | ✅ | ❌ |
| Агрегаты по отделу | ✅ | ❌ |
| Планы менеджеров | ✅ все | только свой |
| Журнал ошибок импорта | ✅ | ❌ |
| Управление планами и справочниками | ✅ | ❌ |

**Принято решение:** менеджер не видит цифры коллег ни в каком виде — ни
поимённо, ни обезличенно, ни в виде средних по отделу. Это влияет на
реализацию: недостаточно спрятать блоки во фронтенде, иначе данные всё
равно уедут в браузер и будут видны в DevTools.

Разграничение реализуется на уровне базы через Row Level Security
(`db/rls.sql`): политика `deals_select` пропускает строку только если
`manager_id = auth.uid()` либо пользователь — РОП. Аналитические вьюхи
объявлены с `security_invoker = on`, поэтому под RLS попадают и агрегаты:
менеджер, запросив помесячную сводку, получит только свою строку.
Фронтенд при этом не обязан ничего фильтровать — он просто рисует то,
что ему отдали.

## 3. Метрики и их определения

Самая частая причина недоверия к дашборду — расхождение в определениях.
Ниже зафиксированы формулы; все экраны считают только по ним.

### Базовые величины

| Метрика | Формула | Примечание |
|---|---|---|
| **Оборот** (`gross_base`) | сумма от клиента × курс | Крупная, но не главная цифра |
| **Комиссия** (`commission_base`) | (сумма от клиента − себестоимость) × курс | **Основной показатель агентства.** План ставится на неё |
| **Маржинальность** | комиссия ÷ оборот × 100% | Показывает качество продаж, а не только объём |
| **Средний чек** | оборот ÷ кол-во продаж | |
| **Туристов** | сумма `Туристов` по выигранным сделкам | |

### Что считается продажей

Продажа засчитывается по **дате брони** (`booked_at`), а не по дате оплаты
и не по дате вылета.

Обоснование: менеджер влияет именно на момент подтверждения брони.
Оплата может растянуться на месяцы, вылет — на полгода; привязка к ним
размазывает результат работы по чужим периодам и делает мотивацию
непрозрачной.

Формально: сделка засчитана, если `booked_at is not null` **и** статус
не `Аннуляция`.

### Аннуляции

Аннулированная сделка вычитается из того периода, в котором была
забронирована, — а не из текущего. Иначе в отчёте за месяц появляются
отрицательные цифры за чужие продажи.

Отдельная метрика: **% аннуляций** = аннулировано ÷ (забронировано +
аннулировано) за период брони.

### Конверсия — пока не считается

**На текущих данных конверсию и воронку посчитать невозможно.** В отчёте
фиксируются только состоявшиеся продажи; обращений клиентов, которым не
продали, в нём нет. Знаменателя не существует.

Чтобы метрика появилась, в таблицу нужна одна колонка — **дата обращения**,
и строки должны заводиться на каждое обращение, а не только на закрытую
сделку. Как только она появится:

`конверсия = сделки, дошедшие до брони ÷ заявки по дате обращения`

Числитель и знаменатель считаются по разным датам осознанно: заявка августа,
забронированная в сентябре, попадает в конверсию августа. Поэтому конверсия
последнего месяца всегда «дозревает» — текущий период помечается как
неполный.

### План/факт

Планы хранятся помесячно на менеджера (`targets`), метрика по умолчанию —
комиссия. Внутри месяца показывается **темп**: сколько должно быть сделано
на сегодняшний день при равномерном выполнении, чтобы прогресс-бар не
пугал третьего числа.

## 4. Экраны

### 4.1. Дашборд РОПа

Период: сегодня / неделя / месяц / квартал / произвольный. Выбранный
период применяется ко всем блокам сразу.

**Ряд KPI-карточек** (верх экрана, 4 штуки):
1. Оборот за период + динамика к прошлому периоду
2. Комиссия за период + динамика
3. Выполнение плана отдела, % — круговой индикатор
4. Заявок / из них бронь — с конверсией в подписи

**Продажи по направлениям** — кольцевая диаграмма, в центре общее число
туристов. Рядом легенда с суммами по каждому направлению. Переключатель
«направления / туроператоры».

**Динамика комиссии** — график по дням или неделям, прошлый период
пунктиром для сравнения.

**Рейтинг менеджеров** — главный инструмент РОПа. Таблица с сортировкой
по любой колонке:

| Менеджер | Заявок | Бронь | Конверсия | Оборот | Комиссия | Ср. чек | План/факт |
|---|---|---|---|---|---|---|---|

Клик по строке → карточка менеджера: та же сетка виджетов, но по одному
человеку, плюс список его сделок.

**Воронка отдела** — заявка → расчёт отправлен → бронь → оплата → вылет,
с процентом перехода между этапами. Наглядно показывает, на каком шаге
теряются деньги.

**Источники лидов** — горизонтальные столбцы: заявок, конверсия и
комиссия по каждому источнику. Отвечает на вопрос «куда лить бюджет».

**Правая колонка «Требует внимания»** — операционка, обновляется постоянно:
* просроченные и подходящие доплаты оператору (≤ 5 дней),
* вылеты в ближайшие 3 дня,
* заявки без движения больше 2 дней,
* аннуляции за период,
* плашка об ошибках импорта, если есть.

Каждый пункт — ссылка на сделку и на менеджера.

### 4.2. Дашборд менеджера

Тот же визуальный язык, другое содержание. Не урезанная копия экрана
РОПа, а личный кабинет.

**KPI-карточки:**
1. Моя комиссия за месяц — крупно, это то, что мотивирует
2. Мой план: факт / план и % с индикатором темпа
3. Мои заявки: всего / в работе / бронь
4. Моя конверсия + средний чек

**Мои задачи на сегодня** — на первом экране, не внизу: доплаты, вылеты,
незакрытые заявки. Для менеджера это главный блок, ради него он откроет
дашборд утром.

**Мои сделки** — таблица с фильтрами по статусу, направлению, периоду.

**Моя динамика** — комиссия по месяцам за последние 6 месяцев, чтобы
видеть свой тренд.

Блоков с чужими данными на экране нет вообще.

## 5. Источник данных

Ежемесячный отчёт по продажам. Сейчас это книга Excel, где **на каждый месяц
заведён отдельный лист** (`май`, `июнь`, `июль`), заголовки — на узбекском,
а сводка по менеджерам лежит сбоку от основной таблицы свободным текстом.

Разбор реального файла и все находки — в разделе 13. Целевой формат колонок,
правила ведения и механика синхронизации описаны отдельно:
[`google-sheets-format.md`](./google-sheets-format.md).

Ключевое:
* синхронизация каждые 15 минут в собственную БД, дашборд считает по ней;
* импорт идемпотентен по `ID заявки`, повторный прогон не плодит дубли;
* битая строка не валит импорт, а попадает в журнал ошибок;
* доступ к таблице — только на чтение.

## 6. Схема базы данных

Полностью описана в [`../db/schema.sql`](../db/schema.sql), политики
доступа — в [`../db/rls.sql`](../db/rls.sql).

Основные сущности:

* **`profiles`** — пользователи и роли, с датами выхода и ухода.
* **`profile_aliases`** — написания имени сотрудника в отчёте. По ним
  импорт связывает строку с профилем.
* **`deals`** — сделки. Центральная таблица. Комиссия и суммы в базовой
  валюте — вычисляемые колонки, руками не вводятся.
* **`payments`** — платежи клиента и переводы оператору, с дедлайнами.
* **`targets`** — планы помесячно, на менеджера или на отдел.
* **`clients`** — клиенты, дедупликация по телефону.
* **`dictionaries` + `dictionary_aliases`** — направления, операторы,
  источники и их синонимы. Без словаря синонимов «Турция», «турция» и
  «Turkey» превратятся в три разных направления.
* **`sync_runs` / `sync_errors`** — журнал импорта.

Три вьюхи (`v_deal_facts`, `v_manager_month`, `v_attention_items`) —
единственное, что читает приложение. Метрики считаются в базе, а не в
браузере: так они одинаковы во всех экранах и не зависят от того, кто
писал компонент.

### Почему разделены даты

В `deals` пять дат жизненного цикла: обращение, бронь, оплата, дедлайн
доплаты, вылет. Это не избыточность — на них держатся разные метрики
(конверсия, засчёт продажи, касса, «горящее», ближайшие вылеты). Свести
их в одну «дату сделки» означает потерять половину аналитики.

## 8. Дизайн-система

За основу берётся утверждённый референс: тёмный интерфейс с лаймовым
акцентом.

**Цвета:**

| Токен | Значение | Применение |
|---|---|---|
| `bg` | `#0A0A0A` | Фон страницы |
| `surface` | `#141414` | Карточки |
| `surface-hover` | `#1C1C1C` | Ховер, строки таблиц |
| `border` | `#262626` | Разделители |
| `text` | `#FAFAFA` | Основной текст |
| `text-muted` | `#8A8A8A` | Подписи, единицы измерения |
| `accent` | `#BEF264` | Акцент, активный пункт меню, кнопки |
| `accent-strong` | `#A3E635` | Графики, заливки |
| `positive` | `#4ADE80` | Рост |
| `negative` | `#F87171` | Падение, просрочка |

**Прочее:** скругления `rounded-2xl` (16px), сетка на 8px, крупные цифры
KPI — 32–40px, подписи — 13px, шрифт Inter.

**Принципы, важнее токенов:**
* Акцентный лайм — только на действии и одном ключевом показателе на
  экране. Если подсветить всё, не подсвечено ничего.
* Цвет несёт смысл: зелёный/красный только про рост и падение, не про
  декор. Рядом с цветом всегда стрелка или знак — иначе показатели
  нечитаемы для дальтоников, а их около 8% мужчин.
* У каждого числа — период и единица. «$3,131,021» без подписи «за
  август, комиссия» порождает больше вопросов, чем ответов.

## 9. Нефункциональные требования

* Загрузка дашборда — до 2 секунд на месячном периоде при ~50 000 сделок.
  Достигается агрегацией в БД и индексами по `(manager_id, booked_at)`.
* Мобильная вёрстка обязательна для экрана менеджера: заявки и доплаты
  смотрят с телефона. Для РОПа достаточно планшета и десктопа.
* Все суммы — в базовой валюте, с фиксацией курса на дату брони. Курс не
  пересчитывается задним числом, иначе отчёты за закрытые месяцы будут
  меняться.
* Часовой пояс фиксируется на уровне приложения; сутки для «сегодня»
  считаются по нему, а не по браузеру пользователя.

## 11. Что не входит в первую версию

Зафиксировано, чтобы не разрастаться:

* ввод и редактирование заявок в приложении (остаётся Google Sheets);
* расчёт зарплат и бонусов менеджеров;
* интеграции с туроператорами и системами бронирования;
* мессенджеры, звонки, переписка с клиентом;
* кабинет клиента.

Схема данных спроектирована так, чтобы пункты 1 и 2 добавлялись без
переделки: в `deals` есть `source_system`, отделяющий импортированные
строки от заведённых вручную, а `targets` уже поддерживает разные метрики
плана.

## 12. Решённые вопросы

1. **Валюта — обе.** Учёт ведётся в долларах, поэтому USD остаётся базовой
   валютой хранения. В интерфейсе стоит переключатель USD / UZS: суммы
   пересчитываются по курсу, который задаётся в шапке. Крупные суммы в сумах
   сокращаются до «млн» и «млрд», иначе они не помещаются в карточку.
2. **Дедлайн доплаты проставляет менеджер** при бронировании. Отдельной
   колонки в текущем отчёте нет — её нужно добавить.
3. **Плана продаж нет** (см. раздел 3). Вместо план/факта дашборд показывает
   расчёт выплат.
4. **Заявок без менеджера не бывает** — в отчёте менеджер указан в каждой
   строке, потому что строка заводится уже по факту продажи. Вопрос вернётся,
   когда в таблицу добавят обращения: там дежурный и общий поток появятся.

## 13. Разбор реального отчёта (май — июль 2026)

Файл `Отчет по продажам.xlsx` разобран скриптом
[`../scripts/parse_report.py`](../scripts/parse_report.py) в
[`../data/deals.json`](../data/deals.json): **105 сделок, 6 менеджеров,
$427 952 оборота и $26 924 прибыли за три месяца**. На этих данных собран
рабочий прототип — [`../prototype/dashboard.html`](../prototype/dashboard.html).

### Что оказалось в файле

| Колонка в отчёте | Значение | Куда легла |
|---|---|---|
| `Брон санаси` | дата брони | `deals.booked_at` |
| `Мижоз И.Ф.Ш` | клиент | `clients.full_name` |
| `Мижоз сони` | количество туристов | `deals.tourists_count` |
| `Хамкор Фирмалар номи` | туроператор | справочник `operator` |
| `Учиш / Қайтиш санаси` | вылет и возврат | `depart_date`, `return_date` |
| `Йўналиши` | направление | справочник `direction` |
| `Пакетни умумий нархи` | брутто | `deals.gross` |
| `Пакетни нетто нархи` | нетто (себестоимость) | `deals.net` |
| `Пакетдан соф фойда` | прибыль | вычисляется, не хранится |
| `Мижоздан олинган пул` | получено от клиента | `payments` (in) |
| `Мижозни пакет учун қарзи` | долг клиента | вычисляется |
| `Пакет учун агентга тўланган` | оплачено оператору | `payments` (out) |

### Новое поле, которого в отчёте нет

**Долг агентства туроператору** = нетто − оплачено оператору. В таблице
такой колонки нет, но обе составляющие есть, поэтому она считается сама.
Это самый горящий показатель из всех: на июль он составил **$13 258 по
шести сделкам** — деньги, которые агентство должно перевести до вылетов.
Увидеть это в Excel можно только вручную сравнив две колонки по всем
строкам.

### Ошибки, которые нашлись при сверке

Дашборд посчитал итоги заново и сравнил с ручной сводкой сбоку от таблицы:

* **Июль недосчитан на $273.** У Шахнозы в сумму вошли сделки на $75 и $88,
  а сделка на $143 потерялась. Ещё $30 и $100 не сошлись у Азизы и Сарвиноз.
  Это прямые деньги: комиссия считается от прибыли, значит недосчитанная
  прибыль — недоплаченная зарплата.
* **Две сделки без нетто** (июль, строки 34 и 50): себестоимость не
  заполнена, прибыль по ним неизвестна. Подставлять сюда брутто нельзя —
  сделка без себестоимости выглядит сверхприбыльной и ломает весь рейтинг.
* **Одна строка без сумм** (июль, строка 48) — есть долг −1200 и больше
  ничего.
* **Одна строка с расхождением** (июнь, строка 10): в отчёте прибыль 150,
  брутто минус нетто даёт 180.

### Что мешает автоматизации

1. **Даты в пяти форматах в одной колонке:** `12.05.2026`, `17/07`,
   `30.06/2026` и ячейки, где Excel сам переставил день с месяцем
   (`11/07` превратилось в 7 ноября). Парсер это разбирает, но правило
   восстановления держится на догадке и однажды подведёт. Нужен единый
   формат и проверка данных в самой таблице.
2. **Числа как текст:** `4548,5` с запятой не суммируется формулами Excel.
3. **Справочники не нормализованы:** `Турция` / `TURKIYA` / `Турция Анталья`
   / `BODRUM` — четыре записи одного направления. Всего 17 направлений
   и 22 оператора после схлопывания синонимов; без словаря их было бы
   вдвое больше.
4. **Имена менеджеров в двух алфавитах** и разном регистре: `Сарвиноз`,
   `сарвиноз`, `SARVINOZ`.
5. **Лист на каждый месяц.** Годовой отчёт превратится в 12 листов, между
   которыми нельзя построить ни одного сравнения.
6. **Сводка сбоку от таблицы** свободным текстом, в разных строках на
   каждом листе, на смеси узбекского и русского. Именно она и содержит
   арифметические ошибки — считается руками.

### Вывод

Переносить в базу нужно не «как есть», а через нормализацию: справочники с
синонимами, единый формат дат, разделение брутто/нетто/оплат. Скрипт разбора
уже это делает и складывает все замечания в журнал — ни одна строка не
теряется молча.

Одно изменение в самой таблице даёт больше всего пользы: **колонка «дата
обращения» и строка на каждое обращение, а не только на продажу**. Она
открывает конверсию и воронку — то, ради чего дашборд обычно и заводят.

## 14. Управление составом команды

Сотрудники приходят и уходят: в разобранном отчёте Мадина и Шахноза
появляются только в июле, в мае их нет. Поэтому список команды живёт
отдельно от продаж, и у руководителя есть экран **«Команда»**.

### Что можно делать

* **Добавить сотрудника** — имя и все написания, под которыми он
  встречается в отчёте. Новый человек сразу может войти в систему, даже
  пока у него нет ни одной сделки.
* **Убрать сотрудника** — снимает доступ и убирает его из текущих
  рейтингов.
* **Вернуть** — если ушёл и вернулся, либо убрали по ошибке.
* **Удалить насовсем** — только для профиля, за которым нет ни одной
  сделки. Ошибочно заведённого человека можно стереть, реального —
  никогда.

### Главное правило

**Убрать сотрудника — не значит удалить его продажи.**

Ушедший пропадает из списка входов и из периодов, где у него нет сделок,
но его прошлые продажи остаются в отчётах и в итогах. Иначе прибыль за
май изменилась бы задним числом, а расхождение в уже закрытом периоде —
худшее, что может случиться с управленческим отчётом: после первого
такого случая цифрам перестают верить.

В рейтинге за период, где у ушедшего есть сделки, он показывается с
пометкой «не работает» — иначе сумма по менеджерам не сойдётся с общей
прибылью. Войти под ним нельзя.

Технически это `profiles.left_at` и `is_active`: строки не удаляются
никогда, у сделки остаётся `manager_id` с ограничением `on delete
restrict`, которое физически не даст стереть профиль с продажами.

### Псевдонимы — не формальность

Импорт связывает строку отчёта с сотрудником по написанию имени, и
написаний у одного человека несколько. В реальном файле:

| Сотрудник | Как встречается в отчёте |
|---|---|
| Сарвиноз | `Сарвиноз`, `сарвиноз`, `SARVINOZ` |
| Абдулкарим | `Абдулкарим`, `ABDULKARIM` |
| Мадина | `MADINA` |

Если у нового сотрудника не заполнить псевдонимы, его строки не свяжутся
с профилем: они попадут в журнал ошибок импорта как «неизвестный
менеджер», а продажи не попадут ни в чей результат. Поэтому поле
обязательно, а система не даёт назначить псевдоним, который уже занят
другим человеком.
